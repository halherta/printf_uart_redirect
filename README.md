# printf_uart_redirect

A CMake-based **STM32CubeMX** project for the **STM32G474xx** that demonstrates how to redirect `printf()` to a UART (serial port) using newlib/newlib-nano and the STM32 HAL.

It also demonstrates a clean way to **keep your own code separate from CubeMX-generated code**, so you can re-open the `.ioc` file, change peripherals, and regenerate without losing or fighting with your application logic.

## Features

- Retargets the C library's `printf()` (and friends) to a UART via the HAL
- Implements retargeting in a dedicated source file, `Core/Src/retarget.c`, using either:
  - `_write()` (newlib's low-level write syscall), or
  - `__io_putchar()` (the weak per-character hook called by CubeMX's default `_write` in `syscalls.c`)
- Keeps user code out of CubeMX-generated `main.c` by using a "fake main" in `Core/Src/app_main.c`
- CMake + Ninja build with `Debug` and `Release` presets (`CMakePresets.json`)
- Floating-point `printf` enabled for newlib-nano via the `-u _printf_float` link option
- Editor support: `.vscode/` and `.clangd` configuration, with `compile_commands.json` export enabled

## How it works

### 1. printf redirection (`retarget.c`)

`printf()` ultimately funnels its output through newlib's `_write()` system call, which writes to file descriptor 1 (`stdout`). By providing our own implementation of that low-level hook, the text can be sent anywhere. Here it is sent to a UART with `HAL_UART_Transmit()`.

`Core/Src/retarget.c` implements one of two approaches:

| Approach | What you implement | Notes |
|---|---|---|
| `_write()` | `int _write(int fd, char *ptr, int len)` | Sends the whole buffer in a single HAL call. More efficient for long strings. |
| `__io_putchar()` | `int __io_putchar(int ch)` | Called once per character by the default `_write` in CubeMX's `syscalls.c`. Simpler, but one HAL call per byte. |

A typical implementation looks like this (illustrative; see `retarget.c` for the actual code and UART handle used in this project):

```c
#include "main.h"
#include <stdio.h>

extern UART_HandleTypeDef huartX;   /* handle generated by CubeMX */

/* Option A: whole-buffer write */
int _write(int fd, char *ptr, int len)
{
    (void)fd;
    HAL_UART_Transmit(&huartX, (uint8_t *)ptr, (uint16_t)len, HAL_MAX_DELAY);
    return len;
}

/* Option B: per-character hook (use instead of Option A) */
int __io_putchar(int ch)
{
    uint8_t c = (uint8_t)ch;
    HAL_UART_Transmit(&huartX, &c, 1, HAL_MAX_DELAY);
    return ch;
}
```

> Use **one** approach, not both. If `_write()` is defined in `retarget.c`, it overrides the one in `syscalls.c` and `__io_putchar()` will never be called.

`retarget.c` is listed explicitly in the top-level `CMakeLists.txt`, so it is compiled and linked into the executable alongside the generated sources.

### 2. Separating generated and user code (`app_main.c`)

CubeMX generates `Core/Src/main.c`, which contains `main()`, system clock setup, and peripheral initialisation. Although CubeMX preserves code placed inside `USER CODE BEGIN/END` blocks, putting real application logic there still ties it to generated files and makes merges and reviews noisy.

This project uses a **"fake main"** pattern instead:

```
 ┌──────────────────────────┐        ┌──────────────────────────┐
 │ Core/Src/main.c          │        │ Core/Src/app_main.c      │
 │ (CubeMX generated)       │        │ (user code)              │
 │                          │        │                          │
 │ main()                   │        │ app_main()               │
 │   HAL_Init()             │        │   application setup      │
 │   SystemClock_Config()   │ calls  │   main application loop  │
 │   MX_xxx_Init()          │ ─────▶ │   printf("...")          │
 │   USER CODE: app_main()  │        │                          │
 └──────────────────────────┘        └──────────────────────────┘
```

- `main.c` stays almost entirely generated. The only user-owned change is a single call into the application, placed inside a `USER CODE BEGIN/END` block.
- Everything you write lives in `app_main.c` (and any further files you add).
- Regenerating from the `.ioc` file only touches generated files, so your application is unaffected.

The `CMakeLists.txt` adds the user sources in its own `target_sources()` block, separate from the CubeMX-managed `cmake/stm32cubemx` subdirectory:

```cmake
target_sources(${CMAKE_PROJECT_NAME} PRIVATE
    # 'fake main' decoupled from STM32CubeMX generated code
    ${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/app_main.c
    # src file containing printf retargeting
    ${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/retarget.c
)
```

This top-level `CMakeLists.txt` is generated by CubeMX **only once** and is never overwritten, so it is safe to edit. The generated sources and HAL drivers live in `cmake/stm32cubemx/CMakeLists.txt`, which *is* regenerated.

### 3. Floating-point printf

newlib-nano omits floating-point support in `printf` by default to save flash. This project re-enables it with a link option:

```cmake
target_link_options(${PROJECT_NAME} PRIVATE
    -u _printf_float
)
```

If you do not need `%f`, remove this option to save several KB of flash.

| Tool | Notes |
|---|---|
| **CMake** | 3.22 or newer |
| **Ninja** | Generator used by the presets |
| **Arm GNU Toolchain** (`arm-none-eabi-gcc`) | Used via `cmake/gcc-arm-none-eabi.cmake` |
| **STM32CubeMX** | Only needed to change peripheral configuration |
| **Debug probe** | ST-LINK (e.g. on-board) or compatible, with OpenOCD or STM32CubeProgrammer |
| **Serial terminal** | PuTTY, minicom, Tera Term, `screen`, etc. |

The project targets C11 (`CMAKE_C_STANDARD 11`, GNU extensions on) and builds with `-Wall -Wextra -Wno-unused-parameter -Wcomment`.

## Building

Clone and build using the provided presets:

```bash
git clone https://github.com/halherta/printf_uart_redirect.git
cd printf_uart_redirect

# Configure and build (Debug)
cmake --preset Debug
cmake --build --preset Debug

# Or Release
cmake --preset Release
cmake --build --preset Release
```

Build output goes to `build/<preset>/` (for example `build/Debug/printf_uart_redirect.elf`). The default build type is `Debug` if none is specified.

## Flashing and viewing output

1. Flash the `.elf` using your preferred tool (STM32CubeProgrammer, OpenOCD, VS Code's STM32 extension, etc.).
2. Open a serial terminal on the UART's COM port / `/dev/ttyACM*` device.
3. Set the baud rate to match the UART configuration in the `.ioc` file (**8-N-1** unless you changed it).
4. Reset the board. Output from `printf()` should appear in the terminal.

## Regenerating code with STM32CubeMX

1. Open `printf_uart_redirect.ioc` in STM32CubeMX (or STM32CubeIDE).
2. Make your changes (pins, clocks, peripherals) and click **Generate Code**.
3. Only generated files are rewritten. `app_main.c`, `retarget.c`, and the top-level `CMakeLists.txt` are left alone.
4. Rebuild.

Things to keep in mind:

- If you **rename or change the UART used for printf**, update the UART handle referenced in `retarget.c`.
- Keep the call from `main()` into `app_main()` inside a `USER CODE BEGIN/END` block so it survives regeneration.

## Adapting to another board or UART
1. Create or update the project in CubeMX for your MCU, enable a UART in *Asynchronous* mode, and select **CMake** as the toolchain/IDE.
2. Add `app_main.c` and `retarget.c` to the `target_sources()` list in `CMakeLists.txt`.
3. In `retarget.c`, point the HAL calls at your UART handle (`huart1`, `huart2`, `hlpuart1`, ...).
4. Add the `app_main()` call to `main.c` inside a `USER CODE` block.
5. Swap the linker script and startup file for your device if you are not using the STM32G474xx.

## Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| Nothing printed | Wrong UART handle or COM port, baud-rate mismatch, or TX pin not routed to the debugger's virtual COM port. |
| Output appears late or only after a newline | stdout is line-buffered. Terminate messages with `\n`, call `fflush(stdout)`, or disable buffering with `setvbuf(stdout, NULL, _IONBF, 0)`. |
| `%f` prints blank or nothing | Confirm `-u _printf_float` is in the link options and that you are linking newlib-nano. |
| `multiple definition of _write` | Both `retarget.c` and another file (for example a `syscalls.c`) define it. Keep only one definition. |
| Hang or garbled output when printing from an interrupt | `HAL_UART_Transmit()` is blocking and not re-entrant. Avoid `printf` in ISRs or use a buffered/DMA approach. |
